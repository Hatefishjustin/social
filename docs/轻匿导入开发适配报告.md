## 一、当前提问箱架构

### 1.1 数据模型（D1）

当前 SoulMirror 提问箱仅有一张核心表 `askbox_questions`（见 `schema.sql` 第 146-157 行）：

```sql
CREATE TABLE IF NOT EXISTS askbox_questions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    asker_id INTEGER,          -- 提问者（可为空=匿名）
    target_id INTEGER,         -- 提问箱主人（users.id）
    content TEXT NOT NULL,     -- 问题内容
    is_anonymous INTEGER DEFAULT 1,
    answer_content TEXT,       -- 回答内容（未回答为空）
    answered_at INTEGER,       -- 回答时间（未回答为空）
    created_at INTEGER NOT NULL,
    FOREIGN KEY (asker_id) REFERENCES users(id) ON DELETE SET NULL,
    FOREIGN KEY (target_id) REFERENCES users(id) ON DELETE CASCADE
);
```

索引：`idx_askbox_target ON askbox_questions(target_id, created_at DESC)`

**关键点**：当前提问箱是**站内闭环**——提问者/回答者都是 SoulMirror 用户，通过 `target_id` 关联。**没有**「外部来源」字段，也没有「导入」概念。

### 1.2 后端 Functions

| 文件 | 路由 | 方法 | 职责 |
|------|------|------|------|
| `functions/askbox.js` | `/askbox` | GET | 查询提问（按 targetId 或广场模式，广场只返回已回答） |
| `functions/askbox.js` | `/askbox` | POST | 提交问题（可匿名） |
| `functions/askbox/answer.js` | `/askbox/answer` | POST | 回答自己的提问（需登录+校验 target_id） |

- 认证：`functions/askbox.js` 与 `functions/askbox/answer.js` 各自**内联**实现了 `getCurrentUser`（未复用 `_lib/auth.js`，属历史遗留）。
- 响应：统一 `jsonResponse`，带 CORS 头。
- 活动日志：提问/回答均写入 `activity_log`。

### 1.3 前端页面

- `qa.html`：轻匿提问箱页面。
  - 支持 `?u=userId` 访问他人提问箱、`?n=name` 快速显示昵称。
  - 两个 Tab：「收到的提问」（mine）与「问答广场」（square）。
  - 分享链接格式：`https://soulmirror.cc.cd/qa.html?u=<userId>&n=<name>`。
  - 通过 `/auth.js` 集成登录（`Auth.*` API）。
  - 调用 `/askbox`、`/askbox/answer`、`/api/user-card`、`/api/avatar`、`/api/view`。

### 1.4 用户系统

- 前端：`auth.js`（全局 `window.Auth`，提供 `isLoggedIn/getUserId/getEmail/getDisplayName/getAvatarUrl/onAuthChange` 等）。
- 后端：`functions/_lib/auth.js` 的 `getCurrentUser(request, env)`（返回 `{id, email, displayName, avatarUrl, isAdmin}`）。
- 会话：`sessions` 表 + `session` Cookie；`functions/session.js` 提供 `/session`。
- 登录流程：`functions/auth/request.js`、`verify.js`、`code-login.js`、`auto-login.js`。

### 1.5 迁移模块模式（重要参考）

现有迁移文件位于 `docs/migrations/`，命名规范 `YYYY-MM-DD-SXX-功能.sql`：

- `2026-08-01-S01-content-violations.sql`

每个迁移文件头部有注释块（项目、日期、说明、执行命令），使用 `CREATE TABLE IF NOT EXISTS` 保证幂等。`schema.sql` 是唯一权威定义，迁移后需同步更新。

## 四、数据库需要哪些字段

### 方案 A：独立导入表（推荐，最小侵入）

新增一张独立表 `lightbox_imports`，与现有 `askbox_questions` 完全解耦：

```sql
CREATE TABLE IF NOT EXISTS lightbox_imports (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,          -- 导入者（SoulMirror 用户）
    url_code TEXT NOT NULL,            -- 轻匿分享ID（来自链接）
    box_title TEXT,                    -- 提问箱标题（ask_box_info）
    question TEXT NOT NULL,            -- 问题内容（ask_box_question）
    answer TEXT,                       -- 回答内容
    source_question_id TEXT,           -- 轻匿原始问题ID（去重用）
    is_public INTEGER DEFAULT 1,       -- 是否公开（is_public_reply=1）
    status INTEGER DEFAULT 1,          -- 轻匿 status=1
    imported_at INTEGER NOT NULL,      -- 导入时间（Date.now()）
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_lightbox_user ON lightbox_imports(user_id, imported_at DESC);
CREATE UNIQUE INDEX IF NOT EXISTS idx_lightbox_dedup ON lightbox_imports(user_id, source_question_id);
```

**优点**：
- 不触碰现有 `askbox_questions`，零风险。
- 独立去重（`user_id + source_question_id` 唯一）。
- 便于后续扩展（如展示、删除、导出）。

### 方案 B：扩展现有 `askbox_questions`（侵入式，不推荐）

在 `askbox_questions` 增加字段：

```sql
ALTER TABLE askbox_questions ADD COLUMN source TEXT DEFAULT 'internal';  -- 'internal' | 'lightbox'
ALTER TABLE askbox_questions ADD COLUMN source_question_id TEXT;
ALTER TABLE askbox_questions ADD COLUMN url_code TEXT;
```

**缺点**：
- 需修改现有查询/写入逻辑，风险高。
- 现有 `target_id` 语义（站内用户）与外部导入不匹配，需额外处理。
- 违反「不破坏现有业务」目标。

> **结论**：采用**方案 A**，独立 `lightbox_imports` 表。

## 五、是否会影响已有功能

### 5.1 不影响

- **现有提问箱**（`askbox_questions`）：方案 A 完全独立，不修改表结构、不修改读写逻辑。
- **用户系统**：新函数复用 `_lib/auth.js`，不改认证逻辑。
- **问答广场**（`/askbox` GET 广场模式）：只查 `askbox_questions`，不受影响。
- **活动日志 / 通知 / 举报**：均不涉及。
- **wrangler.toml / 定时任务 / 中间件**：无改动。

### 5.2 需要注意的点

1. **网络抓取**：轻匿公开数据需从 `qntwx.com` 抓取，属于**服务端出站请求**。需确认：
   - 轻匿公开接口的鉴权方式（是否需要 Cookie/Token）。
   - 抓取超时与失败兜底（参考 `_lib/ai.js` 的 AbortController 模式）。
   - 是否受 Cloudflare Pages Functions 出站网络限制。
2. **数据校验**：导入内容需做长度/类型校验（问题、回答长度上限），防止脏数据。
3. **去重**：同一用户重复导入同一提问箱需幂等（`source_question_id` 唯一索引）。
4. **隐私**：仅导入 `is_public_reply=true` 且 `status=1` 的公开数据，不导入私密问答。
5. **CORS**：新函数需带 CORS 头 + `onRequestOptions`（遵循现有约定）。
6. **认证**：导入接口必须 `getCurrentUser` 校验登录，未登录返回 401。

## 七、关键架构发现：轻匿是 uniCloud 应用（重要）

> 这是本次分析最重要的结论，直接影响数据获取层的实现方式。

### 7.1 现状：轻匿并非「简单公开 REST API」

轻匿（qntwx.com）是一个基于 **uni-app + uniCloud** 的应用。其网页端通过 **uniCloud 客户端 SDK** 访问数据，而非暴露一个可直接 `fetch()` 的公开 REST 接口：

- 数据存放在 uniCloud 的**云数据库集合**（`ask_box_info`、`ask_box_question`）中。
- 前端通过 `uniCloud.database()` / `uniCloud.callFunction()` 访问，走的是 uniCloud 网关协议（通常为 `https://api.next.bspapp.com/client` 或空间专属端点）。
- 该协议需要 **spaceId / provider / clientSecret** 等空间标识，并涉及**请求签名 / 握手**，不是简单的 GET 请求。

### 7.2 对实现的影响

| 原假设 | 现实 | 影响 |
|--------|------|------|
| 直接 `fetch('https://qntwx.com/...')` 抓取公开数据 | 需走 uniCloud SDK 协议 | 无法用普通 HTTP GET 直接取数 |
| 无需鉴权 | 需空间标识 + 签名 | 需逆向/复刻 uniCloud 客户端协议，或寻找替代数据源 |
| 一次请求拿全量 | 可能需分页/多次调用 | 需处理分页与超时 |

### 7.3 可行的数据获取路径（待评估）

1. **复刻 uniCloud 客户端协议**：在 `functions/_lib/lightbox.js` 中实现 uniCloud 网关请求（含签名）。风险：协议可能随版本变化、可能被风控。
2. **抓取网页渲染结果**：若轻匿页面为 SSR 或内嵌 JSON，可抓取 HTML 解析。需确认页面是否把公开问答直接渲染进 HTML。
3. **寻找轻匿官方/第三方开放接口**：若存在公开 API 文档则最稳妥。
4. **人工/半自动导入**：作为兜底，用户手动粘贴问答内容。

> **结论**：在确认轻匿数据获取方式前，**不应直接进入抓取开发**。建议先做一次「协议可行性验证」（抓取一个真实公开链接，观察网络请求与返回结构）。
